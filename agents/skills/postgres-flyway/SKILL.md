# postgres-flyway

Sources: ADR-0004 (one database per service), ADR-0019 (Flyway), `docs/conventions.md` (names, IDs, pagination, optimistic locking), `docs/events.md` (outbox, `processed_event`).

## Migrations

- Plain SQL in `src/main/resources/db/migration`, named `V<NNN>__<what_it_does>.sql` (`V003__add_bio_to_profile.sql`), the next free number in the repo.
- **Never edit a migration that is on `main`.** Fix forward with a new one.
- One purpose per migration; a migration and the code that needs it can share a PR when the PR stays small.
- Hibernate runs with `ddl-auto=validate`: if the entity and the table disagree, the app doesn't start, and the integration tests catch it.
- Every PR with a migration is merged by the owner, after a DBA review.

## Schema rules

- Names: snake_case, singular tables (`profile`, `follow`, `outbox`, `processed_event`).
- Primary keys: `id uuid` (UUIDv7, generated by the service), `NOT NULL` by definition.
- Times: `timestamptz`, stored in UTC; `created_at` on every table, `updated_at` where rows change.
- Strings: `text` with a `CHECK` on length where the API sets a limit (or `varchar(n)`); the database enforces what the API promises.
- **Constraints in the database:** `NOT NULL` wherever a value is required, `UNIQUE` for business keys (username), foreign keys **inside the service's own database** only. Never a reference to another service's data beyond a plain id column.
- **Optimistic locking:** editable rows have `version bigint NOT NULL DEFAULT 0` (JPA `@Version`, exposed as the `ETag`).
- **Indexes:** on every foreign key, and for every query the code runs: keyset pagination needs an index matching the order (for example `(author_id, created_at DESC, id DESC)`). No index "just in case".
- Outbox and `processed_event` tables follow the shape in `docs/events.md`.

## Changes that stay safe once deployed (expand, then contract)

Pixora isn't deployed yet, but migrations are written as if it were:

- **Add a column:** nullable, or with a constant default (fast in PostgreSQL 11+). Make it `NOT NULL` in a later migration after back-filling.
- **Rename or change type:** add the new column, write both, back-fill, switch reads, then drop the old one in a later PR. Never a rename in one step.
- **Drop:** first stop using it in code (one PR), then drop it (a later PR).
- **Big indexes:** `CREATE INDEX CONCURRENTLY`, which can't run inside a transaction. Put it alone in its own migration so Flyway can run it outside one, and check in the integration test that the migration applies.
- **Back-fills** of many rows run in batches, not one huge `UPDATE`.

## DBA review checklist

1. Naming, types, `timestamptz`, `uuid` ids, `NOT NULL` and `UNIQUE` where the rules require them.
2. The migration matches the entity (and the test proves `validate` passes).
3. Every new query has a supporting index; check with `EXPLAIN` in an integration test or describe the plan in the review when it isn't obvious. Look for N+1 patterns in the repository and service code.
4. Locking: does any statement rewrite or lock a big table (type change, `NOT NULL` without default, non-concurrent index)? Is it expand/contract-safe?
5. No cross-service references, no data from another service copied without an event that keeps it updated.
6. The migration was not edited after merge; the version number is the next free one.

Findings use the code-review-task format (`[blocking]`, `[suggestion]`, `[question]`), posted on the PR, with a summary on the sub-issue for the Reviewer.
